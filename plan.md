# Implementation Plan  
## TWIST: Temporal World-relative Intervention, Simulation, and Traceability benchmark for counterfactual explanations.

This plan turns the current model-vs-world benchmark draft into a reproducible evaluation framework suitable for a NeurIPS Evaluations & Datasets submission. It preserves the draft’s core strengths—known temporal SCMs, unit-level replay, CF-faith, do-complexity, and the \(A/B/C\) decomposition—while addressing the key implementation gaps: explicit action semantics, mechanism-access regimes, multi-world uncertainty, intervention feasibility, robustness, traceability, and a real-world bridge.

The proposed duration is **12 weeks**. The schedule assumes one primary researcher with occasional advisor/domain-expert feedback. If there are two developers, the simulator/evaluation workstream and the baselines/experiments workstream can proceed partly in parallel.

***

## Project Objectives

By the end of Month 3, the project should deliver:

1. A benchmark package for temporal, action-grounded counterfactual evaluation.
2. A formal action representation beyond edited observed trajectories.
3. A multi-world synthetic suite with known mechanisms and controlled shifts.
4. An evaluation engine implementing model-relative, mechanism-relative, outcome-relative, actionability, robustness, and traceability metrics.
5. A mechanism-access ladder that compares black-box, estimated-mechanism, and oracle-mechanism explanation regimes.
6. Reproduced and expanded baseline results with uncertainty quantification.
7. A semi-synthetic or domain-inspired bridge dataset.
8. A reproducible paper artifact: code, benchmark cards, datasets, evaluation reports, and manuscript-ready figures/tables.

The current paper already establishes an important prototype: conventional validity may remain high while structural replay fails, and the \(A/B/C\) decomposition can localize whether disagreement comes from trajectory mismatch or classifier–world-label mismatch. The new implementation should preserve this diagnostic while making action semantics explicit and measurable. [draft](184_Does_the_World_Agree_A_Mod.pdf)

# 1. Target System Specification

## 1.1 Core benchmark object

The benchmark should evaluate an explanation as an object:

\[
e = (\mathcal{A}, \hat{x}_{0:T}, y^\star, \mathcal{C}, r, u),
\]

where:

- \(\mathcal{A}\): declared intervention/action plan;
- \(\hat{x}_{0:T}\): explainer-proposed counterfactual trajectory;
- \(y^\star\): requested target outcome;
- \(\mathcal{C}\): constraints invoked by the explainer;
- \(r\): mechanism or rollout model used by the explainer;
- \(u\): uncertainty, confidence, or failure-condition report.

The benchmark world has a temporal SCM:

\[
M^\star = (G^\star, F^\star, P^\star, \ell^\star),
\]

with causal graph \(G^\star\), structural transition functions \(F^\star\), innovation process \(P^\star\), and outcome/label function \(\ell^\star\).

For an action plan \(\mathcal{A}\), the benchmark oracle replays:

\[
x^{\mathcal{A},\star}_{0:T}
=
\operatorname{Replay}(x_{0:T}, \mathcal{A}, M^\star).
\]

This separates:

- the trajectory proposed by the explainer, \(\hat{x}_{0:T}\);
- the trajectory generated by replaying its declared action, \(x^{\mathcal A,\star}_{0:T}\);
- the classifier outcome;
- the world outcome;
- action feasibility and safety.

## 1.2 Minimum evaluation dimensions

The framework should report six families of outputs.

| Dimension | Main question | Example metrics |
|---|---|---|
| Model-relative success | Does the proposal change the classifier prediction? | Validity, logit margin, proximity, sparsity |
| Mechanism consistency | Does the declared action generate the proposed trajectory? | Replay error, CF-faith, effect-profile agreement |
| World-relative success | Does replayed action achieve the target in the true world? | \(A/B/C\), \(V_{\text{world}}\), total disagreement |
| Actionability | Is the action executable under constraints? | Feasibility, safety, cost, duration |
| Robustness | Does explanation quality hold under shifts and uncertainty? | Shift degradation, mechanism sensitivity, stability |
| Traceability | Can an auditor reproduce why this explanation was selected? | Action certificate, provenance completeness, rerun consistency |

The current draft supplies the model-relative, mechanism-relative, and world-relative core. In particular, it defines hard CF-faith, do-complexity \(D\), and the additive disagreement decomposition \(A-C=(A-B)+(B-C)\).  The implementation plan extends that foundation rather than replacing it. [draft](184_Does_the_World_Agree_A_Mod.pdf)

# Month 1 — Build the Benchmark Core

## Week 1 — Protocol, scope, and system design

### Goals

- Freeze the conceptual scope of the benchmark.
- Decide what counts as an explanation, an action, an oracle, and a valid evaluation.
- Create the software scaffold and configuration system.
- Define testable success criteria before running broad experiments.

### Tasks

#### 1. Write the benchmark protocol

Create `docs/evaluation_protocol.md` with:

- benchmark purpose;
- formal definitions;
- evaluated explanation object;
- action tiers;
- mechanism-access regimes;
- factual-unit sampling;
- target-class sampling;
- primary and secondary metrics;
- shift scenarios;
- statistical aggregation plan;
- reporting requirements;
- limitations and claim boundaries.

#### 2. Freeze primary research questions

Use the following four questions:

1. **Model-versus-world gap:** Do trajectory-valid explanations remain target-achieving after replaying their actions through the world mechanism?
2. **Action declaration:** Does requiring explicit action output reduce ambiguity and improve auditability relative to trajectory-only explanation outputs?
3. **Mechanism access:** How do world-grounded success and replay error vary as access to the mechanism changes?
4. **Robustness:** Are conclusions stable across worlds, classifiers, action semantics, noise shifts, and mechanism misspecification?

#### 3. Specify primary endpoints

Set the primary endpoints before implementation:

\[
V_{\text{world}}
=
\Pr\left[
\ell^\star\left(x^{\mathcal A,\star}\right)=y^\star
\right],
\]

\[
V_{\text{safe-world}}
=
\Pr\left[
\operatorname{Feasible}(\mathcal A,x)
\land
\ell^\star\left(x^{\mathcal A,\star}\right)=y^\star
\right],
\]

\[
E_{\text{replay}}
=
\frac{1}{T}
\sum_{t=0}^{T}
d(\hat{x}_t,x^{\mathcal A,\star}_t).
\]

The \(A/B/C\) decomposition remains a primary diagnostic:

\[
A=\Pr[h(\hat{x})=y^\star],
\]

\[
B=\Pr[h(x^{\mathcal A,\star})=y^\star],
\]

\[
C=\Pr[\ell^\star(x^{\mathcal A,\star})=y^\star],
\]

\[
A-C=(A-B)+(B-C).
\]

This builds directly on the draft’s most informative diagnostic. [draft](184_Does_the_World_Agree_A_Mod.pdf)

#### 4. Establish implementation conventions

Decide and document:

- tensor convention: batch × time × channel;
- time indexing convention;
- action serialization format;
- missing-data handling;
- normalization method;
- tolerance policy;
- random-seed policy;
- file naming and artifact versioning;
- expected output schema.

#### 5. Set up CI and quality checks

Implement:

- unit test runner;
- type checks;
- formatting and linting;
- small smoke tests;
- deterministic-seed test;
- artifact-schema test.

### Deliverables

- `docs/evaluation_protocol.md`
- `docs/action_schema.md`
- baseline repository scaffold
- executable toy run:
  - generate one linear world;
  - train one small classifier;
  - replay one atomic action;
  - compute \(A/B/C\);
  - export one explanation certificate.

### Acceptance criteria

- A new user can run one end-to-end toy command from the README.
- All formal objects have unambiguous names and serialized representations.
- The project has no unresolved ambiguity about what is a proposal, action, replay, label, or target.

## Week 2 — Action representations and replay oracle

### Goals

- Implement explicit intervention semantics.
- Generalize beyond the current first-slice/full-schedule diagnostic.
- Implement replay with additive-noise Pearl abduction and deterministic rollout.
- Add action feasibility and cost interfaces.

### Tasks

#### 1. Implement action classes

Implement a common base interface:

```python
class TemporalAction:
    def apply(self, state, t, context):
        ...
    def active_at(self, t):
        ...
    def validate(self, action_space, factual):
        ...
    def cost(self, factual, action_space):
        ...
    def to_dict(self):
        ...
```

Implement four action forms.

| Action type | Representation | Main use |
|---|---|---|
| Point intervention | \(do(X^S_t=a_t)\) | Current draft compatibility |
| Interval intervention | \(do(X^S_{t:t+\Delta}=a_{t:t+\Delta})\) | Treatments and finite-duration control |
| Parametric pulse | \(a_t=\phi(t;\alpha,\tau,\Delta)\) | Smooth or bounded actions |
| High-level control | \(u_t\in\mathcal U\) through \(F(x_t,u_t,\epsilon_t)\) | Actionable recourse |

#### 2. Implement trajectory-to-action adapters

For trajectory-only explainers, implement diagnostic adapters:

- `first_change_atomic`;
- `first_changed_segment`;
- `full_changed_schedule`;
- `sparse_segmentation`;
- `change_point_pulse_fit`.

These should explicitly return:

```json
{
  "is_native_action": false,
  "adapter_name": "first_change_atomic",
  "fit_error": 0.0,
  "action": {...}
}
```

This guards against treating a reconstructed action as if it were claimed by the baseline method.

#### 3. Implement Pearl replay

For additive-noise observed SCMs:

\[
\epsilon_t=x_t-F^\star(\operatorname{Pa}(X_t)).
\]

Then replay an action with factual innovations held fixed:

\[
x_t^{\mathcal A,\star}
=
\begin{cases}
a_t, & \text{for intervened dimensions},\\
F^\star(\operatorname{Pa}(x_t^{\mathcal A,\star}))+\epsilon_t,
& \text{otherwise}.
\end{cases}
\]

Implement:

- `abduct_noise(factual, world)`;
- `replay_pearl(factual, action, world)`;
- `replay_noiseless(factual, action, world)`;
- `replay_interventional_distribution(...)`;
- `validate_replay_inputs(...)`.

#### 4. Implement action feasibility

Start with generic feasibility constraints:

- immutable variables;
- min/max action amplitude;
- min/max state bounds;
- maximum rate of change;
- intervention budget;
- maximum duration;
- minimum lead time;
- forbidden variable combinations.

Represent them as:

```python
class Constraint:
    def evaluate(self, factual, action, replayed_trajectory):
        return ConstraintResult(
            passed=True,
            violation=0.0,
            message="..."
        )
```

#### 5. Implement action cost

Provide both representation-level and domain-level costs:

\[
C_{\text{duration}}=\sum_t \mathbf{1}\{a_t\neq 0\},
\]

\[
C_{\text{magnitude}}=\sum_t \|a_t\|_1,
\]

\[
C_{\text{smoothness}}=
\sum_t \|a_t-a_{t-1}\|_2^2,
\]

\[
C_{\text{budget}} = \sum_t c(a_t).
\]

Do not call the old do-complexity \(D\) “action cost.” Retain it as observed-variable schedule complexity, exactly as the draft warns. [draft](184_Does_the_World_Agree_A_Mod.pdf)

### Deliverables

- Action API with unit tests.
- Pearl replay engine with deterministic controls.
- First-slice, segmented, and full-schedule trajectory adapters.
- Constraint and cost API.
- Technical note explaining native versus reconstructed action semantics.

### Acceptance criteria

- A known one-action structural control has Pearl replay error below numerical tolerance.
- A noiseless control passes noiseless rollout and fails Pearl replay when future factual innovations differ.
- A full-schedule intervention reconstructs the proposed trajectory but receives high schedule complexity.
- Invalid actions are rejected with readable violation reports.

## Week 3 — Metrics, certificates, and structural controls

### Goals

- Implement all core metrics as reusable functions.
- Replace hard-only CF-faith reporting with graded, scale-normalized diagnostics.
- Create explanation certificates and provenance records.
- Validate metrics using positive and negative controls.

### Tasks

#### 1. Implement model-relative metrics

Implement:

- validity;
- probability/logit margin change;
- normalized \(L_1\), \(L_2\), and DTW distance where appropriate;
- feature-, channel-, timestep-, and interval-sparsity;
- temporal smoothness;
- diversity over explanation sets;
- OOD/density score;
- runtime and optimization failure rate.

Use normalized proximity:

\[
d_{\text{norm}}(\hat{x},x)
=
\frac{1}{Tk}
\sum_{t,i}
\frac{|\hat{x}_{t,i}-x_{t,i}|}
{\operatorname{IQR}(X_i)+\epsilon}.
\]

#### 2. Implement mechanism-relative metrics

Implement:

- hard CF-faith under both Pearl and noiseless semantics;
- soft CF-faith:
  \[
  S_{\text{faith}}=\exp(-E_{\text{replay}}/\sigma);
  \]
- normalized replay error;
- effect-profile correlation;
- affected-support overlap;
- retroactivity violation;
- prefix preservation;
- causal-path consistency where graph paths are available.

#### 3. Implement world-relative metrics

Implement the current A/B/C decomposition and additional outcome quantities:

```python
{
  "proposal_model_success": A,
  "replay_model_success": B,
  "replay_world_success": C,
  "delta_traj": A - B,
  "delta_outcome": B - C,
  "delta_total": A - C,
  "action_grounded_success": ...,
  "safe_world_success": ...
}
```

#### 4. Implement traceability metrics

Define an Explanation Provenance Record:

```json
{
  "explanation_id": "...",
  "factual_id": "...",
  "target_outcome": 1,
  "native_action": false,
  "action_semantics": "interval_inferred",
  "action": {},
  "selection_objective": {},
  "active_constraints": [],
  "candidate_count": 0,
  "selection_rank": null,
  "mechanism_access_regime": "R0",
  "proposed_metrics": {},
  "replayed_metrics": {},
  "uncertainty": {},
  "known_failure_modes": []
}
```

Implement traceability checks:

- required-field completeness;
- replay reproducibility;
- configuration-hash consistency;
- action serialization/deserialization consistency;
- objective/rationale availability;
- logged constraint status.

#### 5. Build structural controls

Implement at minimum:

- `PearlSCMRecourse`;
- `NoiselessSCMRecourse`;
- `FullScheduleOracle`;
- `AdversarialTrajectoryEdit`;
- `PlausibleButMechanismWrongEdit`;
- `NoActionAbstain`.

The draft’s Pearl and noiseless controls are essential. Extend them with controls designed to test whether metrics separate plausible appearance from correct causal propagation. [draft](184_Does_the_World_Agree_A_Mod.pdf)

### Deliverables

- `metrics/` package with test coverage.
- Metric specification table in Markdown.
- Explanation certificate generator.
- Positive/negative control suite.
- A synthetic “metric sanity report.”

### Acceptance criteria

- Pearl control gets near-perfect Pearl CF-faith and \(D=1\) for scorable cases.
- Noiseless control gets near-perfect deterministic-rollout CF-faith.
- Full-schedule oracle gets near-zero trajectory replay error but high schedule complexity.
- An adversarial trajectory edit can achieve high model validity but low mechanism consistency.
- All metrics behave as expected on hand-constructed test cases.

## Week 4 — Multi-world synthetic benchmark suite

### Goals

- Build a scientifically varied set of SCM worlds.
- Move beyond one seed, \(L=1\), terminal labels, identity observation, and additive Laplace innovations.
- Create fixed development, validation, and held-out test world sets.

### Tasks

#### 1. Retain and modularize existing worlds

Reimplement the current families:

- stable linear VAR;
- bounded nonlinear masked MLP transition;
- spring/second-order particle system.

The current worlds give distinct dynamics: contractive linear, state-dependent nonlinear, and near-conservative second-order dynamics. [draft](184_Does_the_World_Agree_A_Mod.pdf)

#### 2. Add two new world families

Add:

- **Partially observed state-space SCM**
  \[
  z_{t+1}=F(z_t,u_t,\epsilon_t),\qquad x_t=H(z_t,\nu_t).
  \]
  This introduces observation noise and partial state visibility.

- **Hybrid regime-switching SCM**
  \[
  x_{t+1}=F_{r_t}(x_t,u_t,\epsilon_t),
  \]
  where regime \(r_t\) depends on state or an exogenous process.

These additions make the benchmark less dependent on exact observed-variable abduction.

#### 3. Add generator factors

Vary systematically:

- lag: \(L \in \{1,3,5\}\);
- graph density: sparse, moderate, dense;
- effect strength: weak, medium, strong;
- stability: contractive, weakly stable, oscillatory;
- noise: Gaussian, Laplace, heteroscedastic, correlated;
- observation: identity, noisy, nonlinear;
- confounding: none in exact replay worlds; explicit latent-confounded stress tests in approximate worlds;
- missingness: none, MCAR, temporal block missingness;
- sampling: regular and irregular.

#### 4. Add label families

Implement:

| Label type | Example |
|---|---|
| Terminal threshold | \(X^j_T>\theta\) |
| Interior threshold | \(X^j_{t_{\text{label}}}>\theta\) |
| Distributed exposure | \(\sum_{t=t_1}^{t_2} w_tX^j_t>\theta\) |
| Event onset | threshold crossed before horizon |
| Multi-output label | two linked target conditions |

This addresses the draft’s limitation that all reported labels are terminal thresholds. [draft](184_Does_the_World_Agree_A_Mod.pdf)

#### 5. Create world splits

Create:

- development worlds: visible, with mechanisms;
- validation worlds: visible data, hidden mechanisms for selected experiments;
- held-out test worlds: mechanisms hidden until final evaluation;
- challenge worlds: mechanism shifts and partially observed settings.

Suggested initial sizes:

| Split | Worlds/family | Purpose |
|---|---:|---|
| Development | 10 | Debugging, baseline adaptation |
| Validation | 10 | Hyperparameter selection |
| Test | 20 | Main reported performance |
| Challenge | 10 | Robustness and misspecification |

### Deliverables

- World-generation library.
- World cards for each family.
- Generated data manifests and seeds.
- Train/dev/test/challenge split files.
- Automated integrity checks.

### Acceptance criteria

- Every generated world passes stability, graph, action-space, and label-function tests.
- Each family contains at least one meaningful causal route to the label and one distractor route.
- Multiple mechanisms differ at the world level, not only in sampled trajectories.
- Dataset cards disclose which assumptions allow exact replay and which settings require approximate posterior replay.

## Week 6 — Mechanism-access ladder and native action explainers

### Goals

- Implement the mechanism-access regimes.
- Add action-native explainer controls.
- Quantify what is gained or lost as mechanism knowledge changes.

### Tasks

#### 1. Define access regimes

Implement six regimes:

| Regime | Explainer information |
|---|---|
| R0 | Black-box classifier and factual input only |
| R1 | Observational trajectories for learning plausibility/dynamics |
| R2 | Causal graph \(G\), no transition functions |
| R3 | Transition family and graph, unknown parameters |
| R4 | Estimated mechanism \((\hat G,\hat F)\) |
| R5 | Oracle mechanism \(M^\star\) |
| R6 | Oracle mechanism plus high-level action model and constraints |

#### 2. Implement learned mechanism estimators

Use two estimators:

- baseline transition predictor, e.g. GRU/MLP dynamics model;
- structure-aware estimator, e.g. sparse lagged model or dynamic causal discovery interface.

Do not overclaim discovery quality. Measure:

- graph recovery;
- one-step prediction error;
- rollout error;
- interventional/replay error where intervention data are available.

#### 3. Implement action-native recourse controls

Implement at least:

- **Oracle action recourse** under R6:
  optimize \(u_{t:t+\Delta}\) subject to constraints and replay exactly.
- **Estimated-mechanism action recourse** under R4:
  optimize actions under \(\hat F\), then evaluate in \(F^\star\).
- **Graph-constrained action recourse** under R2:
  restrict candidate action variables to ancestor/actionable sets.

#### 4. Compare mechanism assumptions

For every explanation, record:

- mechanism used by explainer;
- world mechanism used by benchmark;
- mechanism distance;
- action-selection objective;
- realized replay error;
- realized target outcome.

#### 5. Implement mechanism misspecification

Construct controlled errors:

- delete causal edges;
- add spurious edges;
- perturb coefficients;
- perturb nonlinearity;
- alter delay;
- mis-specify noise;
- use wrong observation map.

### Deliverables

- Access-regime configuration files.
- Learned-mechanism modules.
- Native action-recoursing controls.
- Mechanism-misspecification generator.
- First access-ladder plots.

### Acceptance criteria

- Oracle action control achieves high world success subject to feasibility.
- Estimated-mechanism control shows measurable degradation under misspecification.
- The benchmark can attribute whether failures arise from action optimization, mechanism estimation, or classifier/world disagreement.

## Week 7 — Robustness, uncertainty, and action sensitivity

### Goals

- Implement systematic shifts and sensitivity analyses.
- Replace single-point results with uncertainty-aware reports.
- Assess whether explanation conclusions are robust to arbitrary benchmark choices.

### Tasks

#### 1. Implement shift library

Create shifts at four levels.

| Shift type | Examples |
|---|---|
| Innovation shift | Laplace \(\rightarrow\) Gaussian, uniform, heteroscedastic |
| Mechanism shift | coefficients, edge density, delays, nonlinearities |
| Observation shift | sensor noise, missingness, nonlinear sensor transform |
| Decision shift | label threshold, interior label site, classifier retraining |

#### 2. Implement factual perturbation tests

For small perturbation \(\delta\), compare explanation outputs:

\[
\operatorname{Stability}(x,\delta)
=
d_{\mathcal A}
\left(
\mathcal A(x),\mathcal A(x+\delta)
\right).
\]

Measure:

- action onset stability;
- action-variable stability;
- action-cost stability;
- replay-outcome stability;
- explanation target consistency.

#### 3. Add tolerance sensitivity

The draft already shows \(D\) can depend materially on the change threshold.  Evaluate thresholds across a scale-aware range: [draft](184_Does_the_World_Agree_A_Mod.pdf)

\[
\tau \in
\{10^{-5},10^{-4},10^{-3},10^{-2},10^{-1}\}
\times \text{feature scale}.
\]

Report:

- hard CF-faith sensitivity;
- do-complexity sensitivity;
- sparse support sensitivity;
- ranking stability.

#### 4. Implement uncertainty estimates

For stochastic explainers and learned mechanisms, estimate:

- explanation-set variability;
- replay outcome uncertainty;
- bootstrap confidence intervals;
- empirical coverage of target-outcome probability;
- uncertainty under candidate mechanisms.

For a set of plausible mechanisms \(\mathcal M\), report:

\[
p_{\text{robust}}(\mathcal A)
=
\frac{1}{|\mathcal M|}
\sum_{M_j\in\mathcal M}
\mathbf{1}
\left\{
\ell^{M_j}(x^{\mathcal A})=y^\star
\right\}.
\]

#### 5. Build robustness reports

Each method should get a standard report:

```text
Base world success: 0.71 [0.66, 0.76]
Noise-shift success: 0.63 [0.57, 0.69]
Graph-misspecification success: 0.42 [0.35, 0.49]
Action stability: 0.58
Replay-error sensitivity: moderate
Tolerance ranking stability: low
```

### Deliverables

- Shift and sensitivity modules.
- Robustness experiment configurations.
- Uncertainty aggregation code.
- Standardized method robustness report.

### Acceptance criteria

- Every headline metric has an uncertainty estimate.
- Every method has a tolerance-sensitivity profile.
- The framework can identify methods that are model-valid but brittle under mechanism uncertainty.

## Week 8 — Statistical protocol and benchmark validity experiments

### Goals

- Establish that the benchmark itself measures meaningful distinctions.
- Validate metrics with designed controls.
- Finalize the statistical analysis pipeline before full-scale experiments.

### Tasks

#### 1. Construct validity tests

Create controlled pairs where only one dimension differs:

| Test pair | Same property | Different property |
|---|---|---|
| Pair A | Model validity | Mechanism consistency |
| Pair B | Proximity | World success |
| Pair C | Replay error | Action feasibility |
| Pair D | World success | Action cost |
| Pair E | Plausibility | Causal support correctness |

Verify that corresponding metrics separate them.

#### 2. Discriminant validity tests

Ensure metrics do not collapse unrelated properties:

- low replay error should not automatically imply low action cost;
- high plausibility should not imply causal correctness;
- high target validity should not imply safe-world success;
- low total disagreement should not imply good recourse when \(A\) is low.

This formalizes an important insight already present in the draft: a small absolute disagreement can be misleading if the method rarely achieves the target in the first place. [draft](184_Does_the_World_Agree_A_Mod.pdf)

#### 3. Statistical analysis implementation

Use hierarchical bootstrap:

1. resample worlds;
2. resample classifiers within worlds;
3. resample factual units within classifier-world combinations;
4. resample explainer seeds where relevant.

Report:

- mean;
- median;
- 95% CI;
- paired differences;
- standardized effect sizes;
- probability of superiority where useful.

#### 4. Define method comparison policy

No single “best method” score.

Use:

- primary metric table;
- Pareto frontier;
- failure-mode taxonomy;
- paired difference plots;
- per-world distributions.

#### 5. Pilot multi-world study

Run a limited but fully structured study:

- 5 worlds/family;
- 2 classifier architectures;
- 100 factual units/world;
- 3 explainer seeds;
- 5 methods + controls.

### Deliverables

- Benchmark validity report.
- Hierarchical bootstrap implementation.
- Pilot multi-world results.
- Updated protocol v1.0.

### Acceptance criteria

- All positive controls pass their intended metric conditions.
- All negative controls fail at least one relevant criterion.
- Method conclusions do not rely on unpaired point estimates.
- At least one finding from the original draft is replicated across independent worlds.

#### 0. Causal discovery as a mechanism source (added 2026-10-07)

*Status: implemented after Week 8 (`twist.mechanisms.discovery`, `twist discovery`); the study run is
the first Week-9 job.* The R4 Lasso VAR already does Granger-style lagged discovery; proper
discovery methods enter as further R4 estimators. Every discovered graph is scored against the
world's true graph, which real-world causal recourse cannot do.

1. **Discovery estimators at R4.** PCMCI (Tigramite; ParCorr, robust ParCorr or CMIknn tests) and

   true structure, so this is R4 information, not a rung between R2 and R3.
2. **Isolate the cost of the graph.** R3 masked-linear (true graph) vs R4 discovery rows with the
   same fitter. Report the paired ITT world-success difference on identical units.
3. **Score discovery against the truth.** Report summary precision, recall, F1 and SHD, lagged F1,
   and lag accuracy. Relate them to recourse outcomes (C, replay error) with a dose–response from
   controlled graph corruption (deleted and spurious edges) and a PCMCI significance sweep.
4. **Stress-test discovery where its assumptions break** (Week 10): nonlinearity, regime switching,

5. **Graph uncertainty in `p_robust`** (Week 10): build the mechanism ensemble from bootstrap
   discovery runs (graphs and strengths) instead of strength perturbations on the true graph.
6. **TSCausalCF hook.** A discovery step can be TSCausalCF's mechanism source, which evaluates it
   honestly at R4 against the R3/R5 references.

- every discovery graph is scored;

1. **Action clarity:** every explanation has a declared action or is explicitly marked as trajectory-only with a diagnostic adapter.
2. **Replay correctness:** structural controls verify the replay engine under both Pearl and noiseless semantics.
3. **Multi-world evidence:** reported conclusions include uncertainty across independently sampled SCM worlds.
4. **Metric validity:** positive and negative controls demonstrate that metrics distinguish model validity, mechanism fidelity, outcome validity, feasibility, and action cost.
5. **Fair evaluation:** trajectory-only baselines are not accused of violating semantics they never declared.
6. **Robustness evidence:** headline findings are tested under noise, mechanism, and observation shifts.
7. **Traceability:** every result can produce an explanation certificate containing assumptions, action, constraints, selection rationale, replay result, and failure conditions.
8. **Realism bridge:** at least one action-based semi-synthetic domain benchmark is included.
9. **Reproducibility:** an independent clean run reproduces a representative result and figure.
10. **Claim discipline:** the paper distinguishes exact synthetic-world certification from real-world deployment feasibility.

The final framework should make it possible to answer a high-stakes question in a precise, auditable form:

> “What action is being recommended; under which mechanism and assumptions; what trajectory does that action generate for this individual; does it achieve the target outcome; what constraints does it satisfy; how uncertain is this conclusion; and why was this explanation selected?” [draft](184_Does_the_World_Agree_A_Mod.pdf)
